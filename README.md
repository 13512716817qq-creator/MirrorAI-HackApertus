# Mirror AI — Hack Apertus 2026

**Track 2B — Apertus Adoption: Own Project**

Mirror AI is an AI-powered bridge from global demand to the right local path. It turns an unstructured request into a structured service intent, preserves only information explicitly provided by the user, matches relevant resource desks, and routes qualified enquiries toward human follow-up.

## The idea

Cross-border users often know what they need but do not know the correct local workflow.

For example:

> "I want to buy a whole podcast studio equipment from China."

Mirror AI identifies the China-sourcing workflow, extracts the product information, shows relevant sourcing resources, and asks for the missing commercial information instead of inventing a supplier, price, or availability.

The core principle is:

> **AI should structure uncertainty, not manufacture certainty.**

## Why Apertus

Apertus 1.5 is used for the natural-language reasoning layer. The application deliberately keeps deterministic classification, explicit-field extraction, resource matching, and CRM persistence outside the model.

This separation gives the system a practical safety boundary:

- **Deterministic layer:** intent classification, explicit information extraction, required-field validation and resource matching.
- **Apertus layer:** concise natural-language synthesis of the next useful response.
- **Human layer:** final supplier, quotation, booking, medical, legal and commercial decisions.

The project supports an OpenAI-compatible Apertus endpoint and can run locally with a fully offline deterministic demo.

## Architecture

```
User request
     |
     v
FastAPI application
     |
     +--> deterministic intent classification
     |
     +--> explicit-field extraction
     |
     +--> resource matching
     |
     +--> SQLite lead persistence
     |
     +--> Apertus 1.5 adapter
              |
              v
       concise next-step response
```

The model never receives authority to invent commercial facts. The application supplies structured routing context and instructs Apertus to stay within it.

## Core workflows

1. **Buy from China** — procurement, sourcing, samples and coordination
2. **Africa to Global** — commodities, buyer matching and export coordination
3. **Build in China** — company formation and business-partner coordination
4. **Travel in China** — local resources, business visits and custom itineraries
5. **Healthcare in China** — hospital coordination and local support
6. **Study in China** — study destinations and application resources

## Quick start

Requirements: Docker and Docker Compose.

```bash
cp .env.example .env
docker compose build
docker compose up -d
open http://localhost:8000
```

For the reproducible offline demo:

```env
LLM_MODE=demo
```

The UI explicitly identifies demo mode and does **not** claim that the response was generated by a live Apertus endpoint.

## Live Apertus mode

Hugging Face provides an OpenAI-compatible Inference Providers endpoint. Apertus-v1.5-8B is currently available through the PublicAI provider.

```env
LLM_MODE=apertus
LLM_NAME=swiss-ai/Apertus-v1.5-8B:publicai
LLM_BASE_URL=https://router.huggingface.co/v1
LLM_API_KEY=YOUR_FINE_GRAINED_HF_TOKEN
```

The token must have Hugging Face **Make calls to Inference Providers** permission.

Never commit `.env`, API keys, passwords, databases or runtime data.

## Example demo requests

### China sourcing

```
I want to buy a whole podcast studio equipment from China
```

Expected behavior: classify as **Buy from China**, preserve the explicit product, show sourcing resources, and ask for missing quantity, destination and budget.

### Africa trade

```
We produce shea butter in Tanzania and want Chinese buyers.
```

Expected behavior: classify as **Africa to Global**, preserve the explicit commodity and origin, show the relevant trade desk, and ask for missing target market and volume.

### China study

```
I want to study in China in Beijing.
```

Expected behavior: classify as **Study in China**, preserve Beijing as the destination, and ask for missing study level and subject.

## Design and implementation choices

- **FastAPI** for a small, explicit HTTP surface.
- **SQLite/SQLAlchemy** for lightweight CRM persistence.
- **Vanilla HTML/CSS/JavaScript** for a dependency-light interface.
- **Docker Compose** for reproducible deployment.
- **Deterministic matching** to reduce hallucinated suppliers and unsupported claims.
- **Apertus adapter** through an OpenAI-compatible API so the model can be hosted locally or accessed through an approved inference provider.

The Docker image uses the public Amazon ECR mirror of the official Python image to avoid unnecessary dependence on Docker Hub registry access during builds.

## Challenges

The main challenge was making an AI product useful when the inference endpoint is unavailable. The deterministic demo keeps the complete routing workflow testable without pretending that a local fallback is live Apertus.

A second challenge was controlling hallucination risk in cross-border commercial workflows. Mirror AI therefore separates structured facts from generated language and keeps human operators responsible for consequential decisions.

## Security

Secrets are environment-only. The repository intentionally contains no API tokens, customer database or runtime database.
